# نَسَق — وثيقة تأسيس المنتج

**الإصدار:** 1.0 — سبتمبر 2026  
**الحالة:** المرجع التأسيسي للتصميم والهندسة والـMVP  
**إعداد وتطوير:** معتز العلقمي — تعز، اليمن

> **الشعار المفاهيمي:** رتّب عملك، مالك، ويومك في نَسَق واحد.

## 0. طريقة استخدام الوثيقة

هذه الوثيقة هي المرجع التأسيسي لمنتج **نَسَق**. تستخدم لتوحيد قرارات المنتج والتصميم والبرمجة وقاعدة البيانات والصلاحيات والمحاسبة.

**قاعدة حاكمة:** إذا تعارض تنفيذ ميزة جديدة مع الأمان المالي أو فصل مساحات العمل أو الصلاحيات الدقيقة أو قابلية التدقيق، فالأولوية لهذه المبادئ حتى لو أدى ذلك إلى تأجيل الميزة.

- **MUST:** متطلب أساسي لا تطلق النسخة بدونه.
- **SHOULD:** مهم جدًا ويُنفذ ما لم توجد عوائق قوية.
- **COULD:** مفيد ويمكن تأجيله.
- **LATER:** خارج نطاق النسخة الأولى.

## 1. الملخص التنفيذي

نَسَق منصة عربية حديثة تجمع إدارة الأعمال اليومية والمهام والجداول والحسابات والمصروفات والديون والإشعارات والعمل الجماعي داخل نظام واحد، مع مساحات عمل وصلاحيات دقيقة تخدم الفرد والأسرة والطالب والفريق وصاحب العمل والمؤسسات الصغيرة والمتوسطة.

المنتج ليس تطبيق مهام مضافًا إليه قسم مالي؛ بل **نظام تشغيل للعمل والمال والتنظيم**.

### القرار المعماري الأساسي

```text
Web / PWA (Next.js)        Mobile (Flutter لاحقًا)
          \                  /
             Backend API
                 |
        Business / Auth / RBAC
          |        |        |
      PostgreSQL  Redis   Object Storage
          |        |        |
        Ledger    Jobs   Attachments
                 |
        Notifications / Integrations
```

لا تتصل الواجهات مباشرة بقاعدة البيانات في العمليات الحساسة. جميع العمليات المالية والصلاحيات وقواعد العمل تمر عبر Backend/API مركزي.

## 2. الرؤية والرسالة

### الرؤية
أن يصبح نَسَق المساحة الرقمية العربية التي يجمع فيها المستخدم ما يحتاجه لإدارة يومه وعمله وماله وفريقه دون تشتيت بين تطبيقات متعددة.

### الرسالة
تمكين المستخدم من معرفة: ماذا يجب أن ينجز؟ من المسؤول؟ متى؟ كم صُرف؟ لمن؟ وما المتبقي؟ بصورة واضحة وآمنة وقابلة للتتبع.

### القيمة الأساسية
- لوحة واحدة للعمل والمال والوقت.
- فصل المساحة الشخصية عن الأسرة أو الفريق أو المؤسسة.
- صلاحيات دقيقة بدل الأدوار الجامدة.
- محرك مهام موحد لليومي والأسبوعي والشهري والمستقبلي والمشاريع.
- محرك مالي قابل للتوسع إلى محاسبة أعمق.
- إشعارات وموافقات وسجل نشاط للعمل الحقيقي.

## 3. مبادئ غير قابلة للتفاوض

- **البساطة فوق التعقيد:** تخفي الواجهة التعقيد الإداري والمحاسبي.
- **الأمان من الخادم:** Authorization داخل Backend لكل طلب حساس.
- **المال قابل للتدقيق:** لا تعديل جوهري بلا أثر أو حركة تصحيح.
- **عزل مساحات العمل:** لا تسرب بيانات بين Workspaces.
- **العربية أولًا:** RTL أصلي وبنية i18n للتوسع.
- **API موحد:** نفس قواعد العمل للويب والهاتف.
- **MVP مركز:** ما لا يخدم حلقة تنظيم → تنفيذ → تسجيل مالي → متابعة يمكن تأجيله.

## 4. المستخدمون المستهدفون

- **الفرد:** مهام، أموال شخصية، ديون، تنبيهات.
- **الأسرة:** مصاريف مشتركة، التزامات، مهام.
- **الطالب:** جدول، واجبات، أهداف، مصروف.
- **الفريق الصغير:** توزيع أعمال ومتابعة.
- **صاحب العمل:** مصروفات، عهد، ديون، رقابة.
- **المؤسسة:** تنظيم العمل والمال ضمن صلاحيات واضحة.

## 5. Workspaces

المستخدم يمتلك حسابًا واحدًا ويمكنه الانضمام إلى عدة مساحات عمل، ويختلف دوره وصلاحياته في كل مساحة.

أنواع أولية: شخصية، أسرة، فريق، شركة، دراسة.

**قرار بيانات:** كل جدول تشغيلي أو مالي يجب أن يحمل `workspace_id` أو يمتلك مسارًا صريحًا يربطه بمساحة. يمنع الاستعلام العرضي بين المساحات.

## 6. الأدوار والصلاحيات

### الأدوار الافتراضية
- `Owner` — المالك.
- `Admin` — مدير حسب ما يمنحه المالك.
- `Member` — عضو ينفذ ضمن الصلاحيات.
- `Guest` — وصول محدود.

### النموذج الفني
يعتمد نَسَق **RBAC + Granular Permissions**. الدور حزمة صلاحيات ويمكن دعم استثناءات للعضو لاحقًا.

أمثلة:

```text
tasks.view
tasks.create
tasks.assign
tasks.edit_own
tasks.edit_all
finance.view_summary
finance.view_all
expenses.create
expenses.approve
members.view
members.invite
members.edit_role
projects.view
projects.create
projects.manage
reports.view_operational
reports.view_financial
settings.view
settings.manage
```

قواعد:
- لا تعني العضوية إمكانية رؤية كل بيانات المساحة.
- الصلاحيات الحساسة تتحقق Server-side.
- الضيف لا يرث صلاحيات إدارية.
- يمكن إضافة أدوار مخصصة مثل محاسب أو مشرف مشروع.

## 8. الرئيسية — مركز القيادة

يجب أن تجيب خلال ثوانٍ عن:
- ما المطلوب مني الآن؟
- ما المتأخر؟
- ماذا يحدث في المال؟
- ما الذي يحتاج انتباهي؟

مؤشرات محتملة: مهام اليوم، المتأخر، القادم، مصروف اليوم، الرصيد، لي عند الآخرين، عليّ للآخرين، التنبيهات، نسبة الإنجاز.

### موجز اليوم
تجميع المهام والمواعيد والاستحقاقات المالية في Timeline واحد.

الأرقام المالية لا تظهر دون صلاحية مناسبة.

## 9. محرك المهام

محرك واحد يدعم:
- العنوان والوصف.
- المسؤول والمشاركون.
- الحالة والأولوية.
- البداية والنهاية.
- التكرار.
- المشروع/القائمة.
- المهام الفرعية.
- التذكيرات.
- المرفقات والتعليقات.

الحالات الافتراضية:
`جديدة → قيد التنفيذ → بانتظار مراجعة → مكتملة` مع `مؤجلة` و`ملغاة`.

طرق العرض: اليوم، الأسبوع، الشهر، المستقبل، قائمة، تقويم، Kanban، مهامي، مهام الفريق. Gantt/Timeline لاحقًا.

## 10. الزمن والتقويم

- المنطقة الزمنية الافتراضية للعرض: `Asia/Riyadh`.
- تخزين الزمن معيارياً في UTC.
- الميلادي هو الأساس في MVP.
- الهجري عرض اختياري لاحقًا.
- التذكيرات تعمل من الخادم/Queue وليس اعتمادًا على بقاء التطبيق مفتوحًا.

## 11. النظام المالي

يجب أن يبدو بسيطًا للمستخدم وأن يكون منضبطًا داخليًا.

### الحسابات
- نقدي.
- بنك.
- محفظة إلكترونية.
- عهدة.
- حساب افتراضي/تجميعي عند الحاجة.

### العمليات الأساسية
- دخل.
- مصروف.
- تحويل.
- صرف عهدة.
- تسوية عهدة.
- إنشاء دين.
- سداد دين كلي/جزئي.
- تصحيح/عكس موثق.

### المصروف
يحفظ المبلغ، العملة، الحساب، التصنيف، منفذ الصرف، المستفيد، التاريخ، المشروع، الملاحظات، المرفقات وحالة الاعتماد.

### العهد
العهدة رصيد مسؤولية لشخص/جهة. مثال: استلم 10,000 وصرف 7,250؛ المتبقي 2,750 مع كامل التفاصيل.

## 12. الديون والذمم

فصل واضح بين:
- **لي عند الآخرين**.
- **عليّ للآخرين**.

كل دين يحتوي الأصل، الدفعات، الاستحقاق، الحالة والملاحظات.

الحالات: مفتوح، مسدد جزئيًا، مسدد، متأخر، ملغى/مصحح.

**قاعدة مالية:** لا حذف صامت لسداد جوهري؛ التصحيح يجب أن يكون موثقًا.

## 13. المحرك المحاسبي الداخلي

الأساس المقترح **Double-entry ledger** حتى لو لم تظهر مصطلحات المدين والدائن في الواجهة الأولى.

```text
Transaction
  ├── Entry: Account A  Debit/Credit
  └── Entry: Account B  Debit/Credit

Sum(Debits) = Sum(Credits)
```

- لكل عملية `transaction_id` فريد.
- الحركات المرحلة لا تعدل صامتًا.
- الأرصدة تحسب من القيود أو Snapshot قابل لإعادة البناء.
- المالية الشخصية منفصلة منطقيًا عن مالية Workspaces الأخرى.
- Idempotency مطلوبة للعمليات المالية الحساسة.

## 14. المشاريع

المشروع يجمع الاسم والوصف، المدير والأعضاء، المهام، الميزانية، المصروفات، التقدم، الملفات والمدة.

يجهز نموذج البيانات مبكرًا حتى لو تأخرت الواجهة الكاملة.

## 15. الإشعارات والتذكيرات

قنوات:
- داخل التطبيق — MVP.
- Push — عند إطلاق الهاتف.
- Email — اختياري.
- SMS/WhatsApp Business — تكاملات لاحقة فقط.

الاستهداف: عضو، عدة أعضاء، دور، أعضاء مشروع، أو كل المساحة ضمن صلاحية المرسل.

## 16. الموافقات

تدفق Approvals للعمليات الحساسة والمصروفات، مع تسجيل مقدم الطلب والموافق/الرافض والوقت والتعليق.

## 17. Audit Log

يسجل الأحداث الحساسة مثل:
- تسجيل الدخول.
- تغيير دور/صلاحية.
- إنشاء أو تصحيح عملية مالية.
- اعتماد مصروف.
- حذف/أرشفة كيان مهم.

يشمل الفاعل، الإجراء، الكيان، قبل/بعد، السبب، الزمن، وmetadata مناسبة للخصوصية.

## 18. البحث العام

بحث موحد في المهام والأشخاص والمشاريع والديون والعمليات والحسابات، مع تطبيق عزل Workspace والصلاحيات **داخل الاستعلام نفسه**.

## 19. التقارير

- مالية: دخل/مصروف، أرصدة، مصروف حسب التصنيف/الشخص/المشروع، الديون.
- تشغيلية: الإنجاز، التأخير، عبء العمل.
- مشاريع: التقدم والميزانية مقابل الصرف.
- إدارية: نشاط الأعضاء والموافقات والصلاحيات.
- PDF/Excel/CSV لاحقًا حسب الحاجة.

## 20. الذكاء الاصطناعي

طبقة مساعدة فوق البيانات المصرح بها فقط.

حالات استخدام لاحقة:
- موجز اليوم.
- تلخيص المصروفات.
- اقتراح خطة أسبوعية.
- OCR فواتير إلى مسودة.
- تنبيه شذوذ مالي.
- تفسير التقارير.

**قيد أمان:** لا ينفذ AI حركة مالية نهائية أو يمنح صلاحية حساسة دون تأكيد/اعتماد صريح يمر عبر Backend نفسه.

## 21. الهوية وUI

الهوية: تنظيم، ثقة، هدوء، تقنية واتزان مالي دون أن تبدو كبرنامج بنك تقليدي.

اتجاه أولي:
- كحلي عميق أساسي.
- Teal مساعد.
- ذهبي دافئ للتنبيه غير الحرج.
- أحمر معتدل للأخطاء.
- خلفيات هادئة.
- خط عربي احترافي مثل Noto Sans Arabic أو IBM Plex Sans Arabic.

مبادئ الواجهة:
- RTL أصلي.
- كثافة معلومات متوازنة.
- أرقام مالية سهلة القراءة.
- الحالة لا تعتمد على اللون وحده.
- Dark Mode محسوب في Design System.
- Animations قصيرة ووظيفية.

## 22. الهاتف والويب

يبدأ المنتج **Web App متجاوب + PWA**، ويأتي Flutter بعد استقرار V1.

الويب للإدارة والتقارير والكثافة المعلوماتية، والهاتف للإجراءات السريعة والتنبيهات.

## 23. البنية التقنية المرجعية

- Web: Next.js + TypeScript.
- Mobile: Flutter لاحقًا.
- Backend: NestJS + TypeScript.
- Database: PostgreSQL.
- ORM: Prisma أو مكافئ منضبط.
- Cache/Queues: Redis + Worker.
- Files: S3-compatible Object Storage.
- API: REST + OpenAPI/Swagger.
- Deployment: Docker + CI/CD.
- Monitoring: structured logs + error tracking + metrics.

لا تثبت إصدارات المكتبات هنا؛ تختار عند بدء التنفيذ بعد مراجعة الاستقرار والأمان.

## 24. مبادئ API

- كل Request يملك هوية المستخدم وسياق Workspace.
- Authorization قبل الوصول للبيانات الحساسة.
- Idempotency للحركات الحساسة القابلة للتكرار بسبب الشبكة.
- Validation صارم.
- Pagination/Filtering.
- Versioning قبل تغييرات كاسرة عند الحاجة.
- Audit metadata.
- Rate limiting وحماية المصادقة.

- Password hashing قوي مثل Argon2id.
- Access/Refresh tokens أو جلسات آمنة مع rotation/revocation.
- 2FA قابل للإضافة.
- HTTPS فقط في الإنتاج.
- Server-side Authorization.
- Signed URLs/ACL للملفات.
- Backup + Restore testing.
- Audit logs.
- إدارة الأجهزة والجلسات وإبطالها.
- Rate limiting / brute-force protection / CSRF حسب نمط المصادقة.

## 27. الخصوصية

- جمع الحد الأدنى من البيانات.
- عدم كشف الهاتف/البريد بلا حاجة وصلاحية.
- سياسة حذف/إغلاق حساب تراعي الاحتفاظ المحاسبي والقانوني.
- فصل بيانات يمكن حذفها عن سجلات تدقيقية يجب الاحتفاظ بها.

## 28. المتطلبات غير الوظيفية

- ERP كامل للمخزون والمشتريات والرواتب.
- محاسبة ضريبية متعددة البلدان.
- تكامل بنكي مباشر.
- محرر مستندات كامل.
- محادثات فورية بديلة لتطبيقات التواصل.
- AI ينفذ مدفوعات تلقائيًا.
- API عام واسع/Marketplace قبل ثبات المنتج.

## 31. رحلات أساسية

### إنشاء Workspace وإضافة عضو
تسجيل → إنشاء مساحة → ضبط العملة والتوقيت → دعوة عضو → تحديد الدور/الصلاحيات → قبول الدعوة.

### مهمة
إنشاء → مسؤول وموعد وأولوية → إشعار → تنفيذ/تحديث الحالة → إكمال → تحديث موجز اليوم والتقارير.

### مصروف بعهدة
اختيار مصروف → حساب/عهدة → مبلغ/تصنيف/مرفق → موافقة عند الحاجة → إنشاء الحركة → تحديث الرصيد وAudit Log.

### دين وسداد جزئي
إنشاء دين لي/عليّ → الطرف والمبلغ والاستحقاق → تنبيه → دفعة جزئية → تحديث المتبقي والحالة → إغلاق عند الصفر.

## 32. معايير قبول MVP

- لا يستطيع عضو بلا صلاحية مالية قراءة المبلغ عبر UI أو API.
- لا تظهر بيانات Workspace A داخل B أو البحث.
- كل مصروف يغير الرصيد بصورة قابلة للتتبع.
- الدين يعرض الأصل والمدفوع والمتبقي بدقة.
- المهام المتأخرة تظهر في الرئيسية.
- تغيير الأدوار/الصلاحيات يظهر في Audit Log.
- التذكيرات تعمل Server-side.
- RTL يعمل على الهاتف والكمبيوتر.
- retries لا تنشئ قيدًا ماليًا مكررًا عند استخدام Idempotency.

## 34. مراحل التطوير

2. **MVP-Tasks:** Dashboard، Tasks، Calendar، Notifications.
3. **MVP-Finance:** Accounts، Income/Expenses، Debts، Ledger.
4. **V1:** Projects، Approvals، Advanced Audit، Basic Reports.
5. **V1.5:** Flutter + Push.
6. **V2:** Export، Integrations، Files، deeper reports.
7. **V3:** AI Assistant، OCR، intelligent analysis.

## 35. قرارات مثبتة

- الاسم: **نَسَق**.
- العربية/RTL: أساسي.
- Web first: Next.js/PWA.
- Flutter بعد ثبات V1.
- Backend مركزي: قرار أساسي.
- PostgreSQL: قاعدة البيانات.
- Double-entry ledger: أساس مالي.
- Default timezone: `Asia/Riyadh` مع تخزين UTC.
- العملة: أساسية لكل Workspace مع تصميم يدعم تعدد العملات لاحقًا.
- RBAC + Granular Permissions.
- لا حذف صامت للحركات المالية.

## 36. المخاطر

- تضخم المنتج → MVP صارم.
- تعقيد المحاسبة → Ledger + اختبارات + تصحيح موثق.
- تسرب الصلاحيات → Server-side Authorization + Access tests.
- تشتيت الواجهة → Progressive disclosure.
- ضوضاء الإشعارات → Preferences/Priority/Grouping.
- ربط AI بالمال → مسودات + تأكيد + Backend rules.
- اختلاف الويب والهاتف → API موحد.

## 37. صفحة حول

نَسَق نظام متكامل لإدارة المهام والأعمال والحسابات والمصروفات والديون والجداول والفرق، صُمم ليخدم الأفراد والأسر والطلاب وفرق العمل والمؤسسات بأسلوب سلس ومنظم وآمن.

**برمجة وتطوير: معتز العلقمي — تعز، اليمن.**

## 38. تعريف المنتج في جملة
